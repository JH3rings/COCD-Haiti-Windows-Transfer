# 四轮标准结果 vs macOS 迁移结果：口径对齐说明

回答的问题：**「四轮标准结果跟直接从 Mac 迁移过来的结果一致吗？感觉结果都比较差。」**

结论先说：

1. **测试集完全没变**（像素级一致，`11,239,424` px）。
2. **迁移过来那批数字不是同一个协议的产物**，所以"不一致"是预期的。
   迁移版外部席位是**各自原始配置**（Boehm 用 resnet50、epoch/早停/batch 各异）。
3. **v3 的结果确实低**，但拆开看，**只有约 0.04 是阈值造成的，约 0.12 是协议统一造成的。**
4. **真正要你决定的是**：论文主表用不用固定阈值 0.5（见 §5）。

> ⚠️ 一个必须澄清的混淆：`results/` 里其实躺着**两个不同任务**的结果集。
> - **滑坡/COCD 任务**（本次要讨论的）：`rapid_landslide_cocd/`、`ours_v2/`、`grsl_external_baselines/`
> - **单景几何形变检测任务**（另一个任务，与本次无关）：`six_single_sar_distortion_baselines/`
>
> 后者是 `VV,VH,orbit_map → layover/shadow`，划分是 **1199/257/257**，
> 阈值 0.78–0.85，数字高达 F1 0.90。**那是另一个任务的成绩，不能跟滑坡结果混在一张表里比。**
> 本文只讨论滑坡/COCD 任务。

## 1. 先确认：测试集根本没变

这一点最容易被怀疑，所以先排除。

| 来源 | test 总像素 | asc | desc |
| --- | --- | --- | --- |
| 迁移版 `teacher_test_verify.csv` | 11,239,424 | 5,619,712 | 5,619,712 |
| 新 v3 `boehm/test_predictions.npz` | 11,239,424 | 5,619,712 | 5,619,712 |

**完全相等。** 686 views（343 locations × 2 orbits）、128×128 逐像素对齐。
v3 只改了**训练**划分（把 137 个 val 位置并进 train，1233 → 1370），
**test 集一个像素都没动**。所以两组结果可以直接比。

正样本率：814,176 / 11,239,424 = **7.24%**（两组一致）。

## 2. 差异来源之一：阈值（约占 0.04）

### 2.1 迁移版用「验证集搜出来的阈值」

`val_report_v2.csv` 写得很明确：

```
method         reading            threshold  source
Teacher_v2     self (own thr)     0.215     validation/max_f1
Teacher_v2     p4   (own thr)     0.209     validation/max_f1
Teacher_v2     dual (own thr)     0.206     validation/max_f1
```

阈值是 **通过验证集 max-F1 搜索**得到的，落在 **0.206–0.215**，然后把这个阈值
带到 test 上用。注意 `results_R3_seed42.csv`、`teacher_test_verify.csv` 这些"test"
表的列里**只有 `iou`/`f1`，没有 `threshold` 列，也没有 `iou@0.5` 列** —— 因为
它们本就是"搜出来的阈值的成绩"，单独一列。

### 2.2 v3 把阈值永久钉死在 0.5

v3 协议 `threshold: {"source": "fixed", "value": 0.5}`，
`reselect_on_test: false`。而且**取消了 val 划分**，所以物理上也没有数据
可以搜阈值了。结果表里因此同时有 `iou` 和 `iou@0.5` 两列（值相同）。

### 2.3 量化：同一份预测，只换阈值

用 Boehm 的 v3 预测（同一份 `.npz`）在 test 上扫阈值：

| threshold | IoU | F1 | Precision | Recall |
| --- | --- | --- | --- | --- |
| 0.50 | 0.4095 | 0.5810 | 0.7000 | 0.4966 |
| 0.40 | 0.4363 | 0.6075 | 0.6459 | 0.5734 |
| 0.30 | 0.4472 | 0.6180 | 0.5878 | 0.6515 |
| 0.25 | 0.4450 | 0.6159 | 0.5556 | 0.6908 |
| **0.215（≈迁移版阈值）** | ~0.440 | ~0.612 | ~0.54 | ~0.71 |
| 0.10 | 0.3980 | 0.5694 | 0.4351 | 0.8235 |

**Boehm 从 0.5 降到 0.215，F1 涨约 0.03。**这解释了为什么"感觉差"——
0.5 对这类不平衡分割（正样本 6.7%）本来就偏高，模型偏保守。

Boehm 完整的 F1(θ) 曲线（test 集上扫描，仅用于诊断）：

```
 θ      0.90   0.80   0.70   0.60   0.50   0.40   0.35   0.30   0.25   0.20   0.10   0.05
 F1    0.246  0.385  0.476  0.539  0.581  0.608  0.615  0.618  0.616  0.609  0.569  0.521
```

单峰，峰值 **F1=0.6181 @ θ=0.294**。也就是说：

- 固定 0.5 的 F1（0.5810）距该模型自己的最优（0.6181）只差 **0.037**，
  并没有"被 0.5 严重拖累"；
- 真正的最优阈值是 **0.294**，**不是迁移版用的 0.215**。
  两者差 0.08，说明**迁移版那个 0.215 是在它的 val 集上搜出来的、且未迁移到 v3 模型上**。

> 这里要注意一个方法学问题：0.294 是在 **test 集**上扫出来的，
> 属于 oracle 上限，**不能当结果报**。它的价值是说明"阈值敏感度有限"——
> 即便用最优阈值，Boehm 也就 0.6181，**仍然远低于迁移版报的 0.7442**。
> 所以那 0.16 的差距里，阈值只解释约 0.04，**剩下约 0.12 来自训练协议差异**
> （见 §4 第二层）。

## 3. 完整数字对照

### 3.1 外部席位（同一滑坡任务，同一 686 test）

已核实：迁移版这三个数字**确实是滑坡任务的**，用的是**同一个 686 orbit-specific
test 集**、**同一个固定阈值 0.5**（见 `reports/external_baselines_and_kd_cards.md`
开头："All five are measured on the same V1 frozen protocol... 686 orbit-specific
test samples, fixed threshold 0.5"）。**所以阈值不是这两组差异的原因。**

| 方法 | 迁移版 V1（阈值 0.5） | 新 v3（阈值 0.5） | Δ F1 |
| --- | --- | --- | --- |
| Boehm SAR U-Net++ adapted | IoU 0.5926 / F1 0.7442 / AUPRC 0.8363 | IoU 0.4095 / F1 0.5810 / AUPRC 0.6692 | −0.163 |
| CDNetE Early-Fusion adapted | IoU 0.4927 / F1 0.6601 / AUPRC 0.7715 | IoU 0.2404 / F1 0.3877 / AUPRC 0.5304 | −0.272 |
| MFEWF-light / adapted | IoU 0.3232 / F1 0.4886 / AUPRC 0.6583 | IoU 0.2056 / F1 0.3411 / AUPRC 0.4496 | −0.148 |

证据（`reports/all_methods_inventory.md` Block 2 的 "External baselines, same
V3-era convention" 小节也确认了这批数字来自 `results/grsl_external_baselines/metrics.csv`
+ 消融表，阈值 0.5，686 test samples）。

**阈值相同、测试集相同、任务相同 —— 那这 0.16–0.27 的落差从哪来？**

从**训练协议**来。迁移版外部席位用的是**各自的原始训练配置**
（Boehm 用 resnet50、各自 epoch 数与早停策略不一），v3 强制统一成
**resnet34 / 20 epoch / 无早停 / batch 16**。这是"用同一把尺子重测"的必然代价。

> 这里有一个**必须向审稿人交代**的点：迁移版的 Boehm 用 resnet50，
> v3 用 resnet34。参数量 26.0850 M vs 官方 resnet50 版本的 48.9922 M
> （见 `.workbuddy/memory/2026-09-19.md` 第二轮记录）。**骨干缩水是 v3 数字下降的
> 一个直接原因**，而"为了统一"这个理由是否足以说服审稿人，需要你判断。

### 3.2 内部臂（v2 旧口径 vs v3 需重跑）

迁移版 `ABLATION_R1R2R3_SUMMARY.md` 主表（阈值 0.5，但**训练协议是 batch 8 / 50 epoch**）：

| 方法 | overall IoU | overall F1 | overall AUPRC |
| --- | --- | --- | --- |
| Teacher_self（单轨起点） | 0.6006 | 0.7505 | 0.8820 |
| Teacher_dual（双轨上界） | 0.6250 | 0.7692 | 0.8972 |
| Ours R1 | 0.6211 | 0.7663 | 0.8924 |
| Ours R2 | 0.6194 | 0.7650 | 0.8932 |
| **Ours R3** | **0.6298** | **0.7728** | **0.8972** |
| Ours R3g | 0.6260 | 0.7700 | 0.8955 |
| DIS2-port | 0.6272 | 0.7709 | 0.8963 |

注意这张表**写的是阈值 0.5**，和 v3 的思路一致，但**训练配置不同**
（batch 8、50 epoch、早停策略各异）。所以它和 v3 的差距主要来自训练协议，
不是评估口径 —— 这一组必须重跑才能对齐。

## 4. 那"结果差"到底该怎么看

分三层，别混在一起：

**第一层：口径差异（阈值）—— 实测后影响很小**
迁移版外部席位本来就是**固定 0.5** 报的（和 v3 一样）。所以对这批数字，
**阈值不解释任何落差**。（阈值只对 `ours_v2/val_report_v2.csv`、
`results_seed42.csv` 那几条"val 搜阈值"的记录有影响，那不是外部席位。）

**第二层：训练协议差异 —— 这才是主因**
迁移版外部席位是各自原始配置；v3 统一成 resnet34 / 20 epoch / 无早停 / batch 16。
**Boehm 从 resnet50 降到 resnet34** 是其中最硬的一条解释。

**第三层：真实的方法差距（才是要回答的）**
v3 下 Boehm F1 0.5810，CDNetE 0.3877，MFEWF 0.3411。
这三个是同协议、同数据、同阈值下的可比数字。**Boehm 领先 0.19，这才是真信号。**

**另外要正视的一个旧结论**：迁移版卡片里已经写明
"a generic SAR segmentation network with the same single-orbit input is stronger"
—— **上一轮就已经出现"外部基线在固定阈值下压过我们"的情况**，
这正是当初触发 CONDITIONAL GO 的两个原因之一（见
`reports/external_baselines_and_kd_cards.md` Card 1）。所以"结果差"
**不是 v3 引入的新问题，而是早就存在的、v3 让它更明显了**。

## 5. 需要你决定的事

### 5.1 阈值口径（影响主表）

**选项 A：维持 v3，阈值固定 0.5**
- 优点：`reselect_on_test=false` 干净、无阈值泄漏。
- 缺点：数字偏低（F1 0.58 档），不平衡数据不友好。
- 当前协议状态，不用改代码。

**选项 B：回到"验证集搜阈值"**
- 优点：数字好看，是遥感分割文献常见做法。
- 缺点：**必须恢复 val 划分**（推翻 v3 核心决定之一）。
- 代价：训练预算回到 7398 或重新三分，`enforce_protocol()` 要再改回去。

**选项 C：固定 0.5 报主表 + 附录给 F1(θ) 曲线** ← 我倾向这个
- 不需要恢复 val，不改协议，不用重跑。
- 审稿人问"为什么不用最佳阈值"时能正面回答。

### 5.2 更需要你定的一件事：Boehm 的骨干

> **【已撤回 —— 用户 2026-09-19 明确否决】**
> 用户原话："不需要恢复 resnet 50啊，这个 50 的版本不没有问题，
> 因为我们在麦克那里边训练也是这样子的。"
> 结论：resnet50→resnet34 **不是需要修复的缺陷**，应作为协议说明处理
> （外部基线保留各自公布骨干 + 表注说明），不改代码。
> 本节的 (a)/(b) 两个选项与分析**保留仅作记录**，不要再据此行动。

这是我这轮读数据时**新发现的问题**，比阈值重要得多：

> **v3 为了"统一"把 Boehm 从官方 resnet50 改成了 resnet34**
> （参数量 48.9922 M → 26.0850 M，缩了 47%），
> 然后 v3 的 Boehm 只有 F1 0.5810，而迁移版用 resnet50 时有 0.7442。

**如果 Boehm 是论文里最强的外部对照，那把它的骨干砍掉一半是站不住的** ——
审稿人会问"你到底是在比方法，还是在比谁的网络小"。

建议二选一：
- **(a) Boehm 恢复 resnet50**（允许它用官方配置，在表里注明"external baselines
  keep their published backbone"），其余席位保持 resnet34 统一。
- **(b) 全部保持 resnet34** 统一，但**需要把"骨干缩水"写进 limitations**，
  并说明这是为了公平比较而做的主动选择。

我倾向 **(a)**：外部基线保留官方骨干是常规做法，"统一"应该统一训练策略
（lr / epoch / 早停 / 阈值），而**不是统一架构**。架构本来就是被比较的对象。
